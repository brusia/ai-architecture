# ADR-003: Гибридная топология раздачи навыков (Central Gateway)

## Статус

Принято — 2026-11-02

## Контекст

Текущая production-архитектура (`workspace.dsl`, `Prod_Skill_Sharing`) подразумевает обновления
skills при помощи классического механизма git: из репозитория с навыками до агента прямым `git pull`
а публикация нового skill — обычным `git commit/push/PR`. Эта модель упирается в три требования, которые она не
покрывает:

1. Работа в контуре без прямого доступа к внешнему/головному git. LLM-инференс уже
   развёрнут self-hosted (см. [ADR-001](adr-001-llm-hosting.md)); рабочая станция
   DS-инженера в корпоративном контуре может не иметь прямого сетевого доступа к внутреннему 
   git (редкие случаи работы в дороге/без vpn в корпоративный контур).
2. Версионирование и наблюдаемость обновления банка skills. git не даёт ответа на
   вопрос "какая доля команды сейчас на актуальной версии банка", "какие skills реально
   приживаются", "как быстро откатить версию при инциденте" — это осознанный пробел
   [ADR-002](adr-002-data-pipeline-for-agent-experience.md).
3. DS/MLOps-инженер не должен нести на себе релизный цикл дистрибуции. Инженер владеет
   обычным git-flow для *своего* PR (commit/push/PR — это его повседневный инструмент), но
   версии, теги и решение "что сейчас является актуальным банком skills" — это не его
   ответственность и не его экспертиза.

## Рассмотренные варианты

| Вариант | Идея | Плюсы | Минусы |
|---|---|---|---|
| A. Формализовать текущий git-хостинг как Central Gateway | Явно обозначить существующий git-хостинг узлом сети, доступным из корпоративного контура; ничего не менять по существу | Минимальный диф от текущей модели | Не даёт наблюдаемости (adoption/rollback) — git сам по себе не считает, кто на какой версии |
| B. Central Gateway с release-манифестом и агрегированной аналитикой | Тонкий on-prem сервис поверх git: манифест версий, adoption-tracking, обезличенная skill-аналитика, узкая rollback-операция | Даёт observability и управляемый откат; не создаёт второго источника истины — git остаётся каноничным; инженер полностью изолирован от релизного цикла | Новый эксплуатируемый сервис, требует владельца, мониторинга и поддержки |
| C. Offline-first через существующий registry (`pypi-local / artifact storage`) | Публиковать skills_distribution как подписанные release-бандлы в уже существующий в модели `registry` | Не вводит новый компонент — `registry` уже есть в C4 | Не даёт аналитики; registry не предназначен для такого типа релизного цикла (версии skills, а не пакетов/артефактов модели) |

**Выбран вариант B.** Он единственный закрывает все три требования Context одновременно:
офлайн-доступность (Gateway живёт в том же корпоративном контуре, что и LLM-кластер — ADR-001),
наблюдаемость и управляемый rollback, и полную изоляцию инженера от релизного цикла.

## Решение

Вводим новый контейнер **Central Gateway** (on-prem, в `workspace.dsl` — `prod.gateway`) и три
новые роли, разделяющие ответственность за content-review, релиз-инфраструктуру и решение об
откате.

### Central Gateway — не второй источник истины, а зеркало + observability

Git-репозиторий Profile Distribution (`skills_distribution`) остаётся **единственным источником истины** для
содержимого. Gateway состоит из четырёх компонентов (`workspace.dsl`, `Prod_C3_Component_Gateway`):

- **Release Manifest Service** (`gw_manifest`) — `GET /distribution/latest`,
  `GET /distribution/{version}/manifest.json`. Манифест генерируется CI-джобом на каждый push
  git-тега — тонкий слой метаданных над git, без собственного состояния "что сейчас активно".
  `hermes profile update` обращается сюда, а не к git напрямую — инженер никогда не видит
  версии/теги.
- **Adoption Tracker** (`gw_adoption`) — принимает обезличенные чекины
  (`{profile_hash, distro_version, timestamp}`) при каждом `profile update`. Даёт обзор, какая
  доля команды на актуальной версии.
- **Skill Analytics Aggregator** (`gw_analytics`) — принимает обезличенную числовую статистику
  применения skill (`success_count`/`failure_count` по имени, БЕЗ кода/diff/содержимого) —
  источник для решения о rollback.
- **Rollback Trigger** (`gw_rollback`) — узкая auditable операция `rollback(version)`.

### Роли и разделение ответственности

| Роль | Экспертиза | Ответственность |
|---|---|---|
| DS/MLOps-инженер | Ведёт миграцию по протоколу | Обычный git commit/push/PR для своего skill; `hermes profile update` через Gateway (не видит версии/теги/релизный цикл) |
| Skills Owner (новая) | ML/миграционная экспертиза, фазы 0-11 | Content-review PR (double approval, см. ниже); узкое право отката `rollback(version)` через Gateway API |
| MLOps Reviewer (новая) | CI/deploy экспертиза, фазы 12+ | Content-review PR наравне со Skills Owner — approve обязателен для merge независимо от фазы, т.к. skill может затрагивать обе области |
| DevOps (новая, Gateway Operator) | Платформа/релиз-инженерия | Владеет инфраструктурой Gateway и CI-пайплайном (авто-релиз на merge); технически исполняет rollback по запросу Skills Owner; не участвует в content-review |
| `lead` (сужена) | Общее владение продуктом | Дашборды/алерты (observability), без прямого участия в review/release (может быть добавлен как ) |

**Content review — double approval, не разделение по фазе.** Каждый PR со skill требует approve
и от Skills Owner, и от MLOps Reviewer — не только для skills соответствующей их фазе, потому что
skill может затрагивать обе области одновременно (например, изменение экспорт-логики влияет и на
downstream CI-джобы).

**Forward-релиз — полностью автоматический.** CI на каждый merge в `main` дистрибуции сам бампает
версию, ставит git-тег и публикует манифест в Gateway — без ручного шага и без участия
content-ролей.

**Rollback — единственный ручной путь, с разделением decision/execution.** Рассмотрены два
подварианта:

- **B1 (выбран).** Git остаётся единственным источником истины: откат = обычный git revert +
  новый тег, публикуемый тем же CI-механизмом, что и форвард-релиз. Skills Owner инициирует через
  узкую auditable Gateway-операцию `rollback(version)` — "big red button", не требующий доступа
  к инфраструктуре; технически исполняет DevOps.
- **B2 (отклонён).** Gateway хранит собственное состояние "активная версия", позволяющее
  мгновенный откат без нового git-релиза. Даёт более быстрый отклик при инциденте, но вводит
  второй источник истины (git HEAD vs Gateway state), что создаёт риск рассинхронизации и
  требует отдельного аудита состояния Gateway.

Выбор B1 обоснован тем, что единственность источника истины важнее скорости отклика на этом
масштабе: миграции не мгновенны (часы/дни), и задержка в один CI-цикл на rollback не критична,
тогда как второй источник истины — постоянный источник рассинхронизации.

Разделение "кто решает" / "кто исполняет" реализует принцип разделения ответственности. Skills Owner
получает не административный доступ к платформе, а узкое, предопределённое действие
(`rollback(version)`). DevOps не принимает решений о содержании skills — не его
экспертиза; Skills Owner не администрирует Gateway/CI — не его экспертиза.

## Последствия

### Преимущества

- Рабочая станция DS/MLOps-инженера не нуждается в прямом доступе к внешнему/головному git —
  Gateway живёт в том же корпоративном/on-prem контуре, что и LLM-кластер (ADR-001).
- Явная observability: adoption (доля команды на актуальной версии) и skill-аналитика
  (success/failure), которых не было при чистом git-хостинге.
- Управляемый rollback без необходимости заводить тикет и ждать платформенную
  команду — при этом без компрометации разделения ролей.
- Git остаётся единственным источником истины для содержимого — Gateway не дублирует и не может
  разойтись с ним по состоянию.
- Memory-инвариант (hard-excluded `memories/`) не затронут — Gateway работает только с
  git-содержимым (skills) и обезличенными метриками, но никогда с памятью между сессиями.

### Риски

- Новый эксплуатируемый сервис — требует владельца (роль DevOps) и мониторинга собственной
  доступности; если Gateway недоступен, `hermes profile update` не работает, даже если git
  доступен.
- Двойной approval увеличивает цикл ревью каждого PR по сравнению с единственным ревьюером
  (признано несущественным)
- Rollback ограничен временем одного CI-цикла (вариант B1), не мгновенный — осознанный компромисс
  в пользу единственности источника истины.
- Требуется явный RBAC на Gateway API (кто может вызвать `rollback`, кто — только `profile
  update`) — дополнительная поверхность конфигурации в IdP/Vault (`workspace.dsl`,
  `prod.gateway -> idp`).
